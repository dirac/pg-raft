# `raft` — Consensus over the WAL stream

Source: `src/raft/`. The module is built, and it is tested by `raft_log_test` plus four in-process
ensemble tests.

## 1. Purpose

Elect one leader node, whose PostgreSQL runs as the primary, and replicate its WAL to the other
nodes so that:

- A commit is acknowledged to a client only after its WAL is durable on a **majority**.
- A follower's standby replays WAL only up to the **committed** point.
- On leader failure, a node with the most complete log wins the election and promotes its
  standby.

The Raft log does not contain SQL or client requests. It contains **WAL file operations
generated by the primary itself**: the leader's FUSE layer turns each intercepted write and fsync
into an entry. The WAL bytes travel alongside the entries.

## 2. Data model

### 2.1 Entry and command (`raft_types.h`, `wal_types.h`)

```cpp
struct Entry { std::time_t time; RaftTerm term; WalCommand cmd; };

struct WalCommand {
  LogSeqNumber                 flushed_lsn;   // the primary's flush LSN: safe to stream up to here
  optional<LogSeqNumber>       segment;       // the WAL segment of the op
  variant<monostate,           // tick entry
          FlushOp{off,size},   // fsync of [off, off+size): the durability barrier
          OpenOp, CloseOp,
          WriteOp{off,size},   // bytes [off, off+size) of `segment`; the bytes are sent alongside
          TimelineOp{tli, content}> command;
};
```

### 2.2 WAL payload (`MemBlock`)

An entry only names a region; the bytes go in the same message as the request:

```
[ net header: data size, attached size, xxhash32 of each ]
[ RaftRequest (binary archive, incl. data = up to 2 MemBlocks) ][ block0 bytes ][ block1 bytes ]
```

- `RaftPeerConnection::mem_blocks(entries)` takes the union range of the `WriteOp`s in each
  segment. `trim()` cuts a batch so that it touches at most **2 segments**.
- `send_request` **copies** the block bytes out of the segment mmap into a buffer owned by the
  request, then attaches that buffer. The copy is required: PostgreSQL keeps writing into the
  segment and rewrites its last page, so sending directly from the mmap lets the bytes change
  between computing the frame checksum and writing the socket. The ensemble tests caught exactly
  this.
- The follower receives `(RaftRequest, bytes)` through `read_data_and_buff()`. It checks that the
  block sizes add up to the bytes received. The server writes and msyncs the bytes **only after**
  it has accepted the request (term current, log matching). So a request from a deposed leader
  never touches the WAL, and a successful `AppendEntriesResponse` means the bytes are durable on
  that follower.

### 2.3 State machine (`raft_state.h`)

`RaftState` is the state machine. The replicated data is the WAL in the
segment files, which is written as entries are received. "Applying" an entry only advances a
position:

| Field | Meaning |
|---|---|
| `log_idx` | last applied entry |
| `timestamp` | time of the last applied entry |
| `flushed_lsn` | highest `flushed_lsn` applied: the committed WAL a standby may replay |
| `needs_backup` | set when the log was replaced by an InstallSnapshot; the WAL before the snapshot's segments is missing until a PostgreSQL backup restores it |
| `wal_end` | highest end (segment + offset + size) of the `WriteOp`s applied: the end of the WAL in `wal_dir`. A new leader's standby replays up to it before promotion (see [node.md](node.md#32-promotion-became_leader)). A maximum, because a rewritten page is published again over earlier offsets. It can end inside an incomplete record |

A `RaftObserver` (set by the node) receives `applied(idx, entry, state)` for each applied entry,
`installed(state)` after a snapshot, `became_leader(term)` at full leadership (once every
inherited entry is committed and applied) and `stepped_down(term)` when a leader becomes a
follower (after its pending `exec()` handlers have failed). It runs with the server lock held and
must not block. On a follower, `applied` advances the WalSender to `state.flushed_lsn`.

`set_needs_backup(bool)` sets and persists `RaftState::needs_backup`. While it is set the node
doesn't start elections and doesn't take one from a `RequestElection`; it still votes and
replicates (`raft_ensemble_needs_backup_test`).

### 2.4 Persistent state (`RaftLog`, LMDB)

`RaftLog` keeps:

- Page checksums (xxhash32) and 16 KiB pages.
- The thread-local check that no transaction or cursor leaks.
- A background sync thread, unless `sync_commits` is set (`no_sync` is for tests only).

| File | Contents |
|---|---|
| `term.lmdb` | `"term"` → u64 (the term only moves forward, and a new term clears the vote), `"vote"` → node |
| `logs.lmdb` / `logs_` | `(idx BE, term BE)` → binary-archived `Entry`. A sentinel `(0,0)` is written on creation |
| `logs.lmdb` / `meta_` | `"state"` → `RaftState` |

Operations:

- `append_entries(prev_idx, prev_term, entries, delete_entries)`:
  - Leader path: append only after the last entry.
  - Follower path: delete everything after a matching `(prev_idx, prev_term)`, then append.
  - On `MDB_MAP_FULL` the map grows ×4. On `MDB_TXN_FULL` the batch is split in half.
- `entries_from(idx, n)` (`nullopt` if `idx` was compacted), `latest_entries(n)`, `get_term(idx)`.
- `save_snapshot(state, keep)`: store the state, then delete entries before
  `state.log_idx - keep`.
- `install_snapshot(log_idx, entries, state)`: replace the whole log with `(log_idx, …]` and store
  the state.

## 3. Protocol

The message types:

```
RaftRequest  { term, node_id, variant<monostate /*ping*/, RequestVote, AppendEntries,
                                      InstallSnapshot, RequestElection> request,
               RequestResponseInfo info, inplace_vector<MemBlock,2> data }
RaftResponse { term, node_id, variant<monostate, RequestVoteResponse, AppendEntriesResponse,
                                      InstallSnapshotResponse, RequestElectionResponse> response,
               RequestResponseInfo info }
```

Every request gets a response. `RequestResponseInfo` carries `request_term` (stale responses are
ignored) and a sequence number for each request type, which is used to count outstanding requests
without locks.

### 3.1 Topology

Every node opens one outbound `RaftPeerConnection` to each peer at `servers[i].ha_port`, with the
handshake identity `Raft:<id>`. It sends its own requests and reads the responses on these
connections. It receives peers' requests on inbound `RaftFollowerConnection`s. Any other identity
gets a `RaftClientConnection` (§6). `PeerConnectionMgr` reconnects closed slots every
`reconnect_interval_msecs`. A peer that connects to us triggers an immediate reconnect back to it.

### 3.2 Elections

- **Gathering terms.** A node that restarts with term 0 pings its peers. It votes only after a
  majority has answered, so it never votes in a term it has already seen.
- **Randomized timeout.** The election timeout is drawn once per ping, uniformly from
  `[T + 20·id, 2·(T + 20·id)]`. Drawing per ping rather than per check avoids split votes.
- **Candidate.** It persists `term + 1`, votes for itself, and sends `RequestVote{last_entry}`.
- **Voters** refuse a stale term, refuse when they can't vote yet (`!can_vote`), and refuse a
  candidate whose log is older. Otherwise they grant one vote per term, persisted.
- **Two-phase leadership.** A candidate with a majority sends AppendEntries, and only becomes
  `kLeader` once `commit_idx == last_entry`. Until then it does not `exec()` anything, so the new
  primary has every WAL byte that a previous primary acknowledged.
- **Step-down** (`stepdown()`, also called on shutdown): the leader forces a tick, sends
  `RequestElection` to the first peer that has the tick, and that peer becomes a candidate at once.
  If no peer takes over within 32 election timeouts, the step-down is called off.

### 3.3 Replication

- `exec(cmd, handler)` runs on the leader only. It appends `Entry{now, term, cmd}` and records the
  handler under its index. The handler is called with the index when the entry commits, or with
  `ErrorCode::kNotLeader` if the node is not the leader, stops being the leader, or closes. The
  handler runs with the server lock held, so it must not call back into the server.
- `send_append_entries`:
  - When the peer is caught up, an AppendEntries is sent at most every `election_timeout/4`; it
    doubles as the heartbeat.
  - Otherwise it sends up to `max_entries` entries, trimmed to 2 segments, with their blocks.
  - If the needed entries have been compacted, it sends InstallSnapshot instead.
- **Follower:**
  - Reject a stale term.
  - Become a follower.
  - Accept only if `prev_log_idx >= commit_idx` and the log matches.
  - Write the blocks.
  - Set `commit_idx = min(leader_commit, last new)`.
  - On a mismatch, reply `{idx, term at idx, n}`, where `n` is the run of uncommitted entries with
    that term.
- **Leader on response:**
  - Success: `in_sync`, then the match index. The commit index is the highest index held by a
    majority (`MatchIndexes` counts peers only, quorum `n/2`, because the leader's own copy is
    implicit). Then apply.
  - Failure: walk back up to `min(n, 64)` entries looking for a match. If there is no term to
    compare (`term` missing) or the entry has been compacted, send InstallSnapshot.
- **Ticks:** the leader appends a tick entry if it has appended nothing for `tick_seconds`.

### 3.4 Apply

`apply_entries()` runs under the server lock. For each entry in `(applied, commit_idx]` it calls
`state.apply`, then `applier->applied`, then the leader's handler for that index. Ticks and
entries inherited from earlier leaders have no handler.

### 3.5 Compaction and snapshots

- **Compaction**: after `compaction_lag` entries have been applied since the last compaction, a
  node saves its `RaftState` and deletes entries older than `log_idx - keep_old_logs`. Planned:
  the boundary becomes `keep_from`, the segment of the latest backup's end LSN
  (`set_wal_keep_from`, see [backup.md](backup.md#5-wal-retention-and-raft-compaction)), and
  `keep_old_logs` goes away. Every entry must have its WAL in `raft/wal` (an entry only names a
  segment, offset and size), so segments are deleted in a separate step, on another thread, only
  before the oldest entry's segment, which compaction records in `RaftState` (`first_idx`,
  `first_segment`) in the same transaction as it deletes the entries.
  **The leader compacts too.** Stepping down to compact would mean a PostgreSQL failover. Entries
  are small (the WAL is in the segments), so compacting on the leader is cheap.
- **InstallSnapshot, phase 1 (raft)**: the leader sends its latest `snapshot_entries` entries,
  trimmed to those that touch at most 2 segments, together with the **full contents** of those
  segments, its applied `RaftState`, and its latest timeline history file, if any
  (`InstallSnapshot::timeline`; the `TimelineOp`s that wrote it may be compacted away). The
  follower writes the segments and the history file, and installs the entries with the leader's
  state (`needs_backup = true`). If the state's `log_idx` is within the entries, the follower has
  applied them up to it (the leader has, and their WAL is in the segments); otherwise, when the
  leader applies far behind its log, the follower keeps the state's values at the snapshot's
  `log_idx` (they come from earlier entries, so they are never ahead). It sets `commit_idx` to the
  state's `log_idx` and can follow the leader from there at once. The connection reads the state
  from a copy the server publishes under its own mutex (`applied_state()`), since it holds the
  connection's lock, not the server's.
- **Phase 2 (PostgreSQL backup)**: a node with `needs_backup` restores the latest backup from the
  cluster's backup store ([backup.md](backup.md)), then replays the backup's WAL and streams the
  rest from `raft/wal` (see [node.md](node.md#43-recovering-from-needs_backup)). The node logic is
  not yet written (§8). Backups no longer come from peers, so the client channel's
  `SnapshotRequest` and `set_backup_provider` are unused by the node design (§6).

## 4. Integration with `wal_fuse` and `wal_sender` (node, to be written)

| Where | What |
|---|---|
| Leader `WalTracker::async_publish(seg, off, size)` | `exec(WalCommand{flushed_lsn, seg.lsn, WriteOp{off,size}}, …)` |
| Leader `WalTracker::async_fsync(seg, off, size, cb)` | `exec(WalCommand{…, FlushOp{off,size}}, h)`. `h` calls `cb(ok)` on commit, or `cb(kNoConsensus)` on `kNotLeader`. PostgreSQL's fsync, and therefore its commit, returns only after quorum. |
| Follower `RaftObserver::applied` | `WalSender::advance(state.flushed_lsn.lsn)` |
| Every node | `set_pg_status(...)` from a `PgClient` poller, `set_serving(true)` once the leader's PostgreSQL is promoted, and `set_needs_backup(...)` (planned) when it has no usable data directory |

`RaftServer::segment(lsn)` opens segments in the server's `wal_dir` through one
`WalSegmentCache`, and creates a missing segment, zero-filled. In the node design `wal_dir` is
`raft/wal`, separate from the FUSE backing directory `pg/pg_wal` (see
[node.md](node.md#directory-layout)).

## 5. Concurrency

The model:

- Role and term state are atomics, and role transitions take `mtx_`.
- `usage_lock_` (shared) guards against shutdown. Request and response handlers take it, and
  `close()` takes it exclusively.
- Each `RaftPeerConnection` serializes its sends with `mtx_`.
- `RaftLog` has one writer and many readers.

## 6. Client channel (`client_types.h`)

`RaftClientConnection` serves non-Raft identities, such as the proxy.

- **Leadership by heartbeat**: `status()` is `0x3` when the node is the leader and serving, `0x1`
  when it is the leader but not serving, and `0` otherwise. `RaftServerConnection` exposes
  `is_leader()`, `is_serving()`, and `async_leadership_check()`.
- `StatusRequest` → `StatusResponse{leader, applied_idx, primary_flushed_lsn,
  standby_applied_lsn}`.
- `SnapshotRequest{applied_idx}` → `SnapshotResponse{success, files, links}`, followed by each file
  (`write_file`, xxhash32 per chunk). A server behind `applied_idx` refuses. The backup itself
  comes from the server's backup provider. `RaftServerConnection::backup(dir, applied_idx)`
  receives the files into `dir` and recreates the links. **Unused by the node design:** nodes
  restore from the backup store instead ([backup.md](backup.md)), so this request and
  `set_backup_provider` are candidates for removal.

## 7. Testing

| Test | What |
|---|---|
| `raft_log_test` | fault injection (every LMDB call fails in turn, and no txn or cursor leaks), plus appends and conflicts, entries and latest entries, snapshot and compaction, `install_snapshot`, term and vote, key encoding |
| `raft_ensemble_sanity_test` | 5 nodes for 20 s under the Writer |
| `raft_ensemble_leader_stopped_test` | the leader crashes 3 times and restarts |
| `raft_ensemble_stepdown_test` | 4 hand-overs via `RequestElection` |
| `raft_ensemble_snapshot_test` | a follower loses its files while the others compact. It must receive an InstallSnapshot **while the leader is under load** and catch up with `needs_backup` set. |

The **Writer** plays the primary. It writes random bytes into the leader's segments at increasing
offsets, calls `exec(WriteOp)`, and calls `exec(FlushOp)` from time to time.
`RaftTestService::check_consistency` then checks:

- Log matching across the running servers.
- That servers which applied the same entries have the same state.
- That every acknowledged write is an accepted entry.
- That every server has identical bytes for every acknowledged write it applied (by xxhash32).

## 8. Open items

1. **Node**: wire `WalTracker`, `RaftObserver`, `PgInstance`, `PgClient` and `WalSender` into a
   pg-raft node process (§4), including `set_serving` once promotion is done.
2. **Phase 2 of a snapshot**: when `needs_backup` is set, restore the latest backup from the
   backup store, then clear `needs_backup` (`set_needs_backup`, to be added; while it is set the
   node must not start elections).
3. `OpenOp` and `CloseOp` need FUSE hooks; today only writes, fsyncs and timelines (a rename to
   `<timeline>.history`, `WalTracker::async_timeline`) are generated. Applying a `TimelineOp`
   writes the history file into `wal_dir` on every node.
4. WAL retention: segments are never removed from `raft/wal`, and the renamed `.X` segments are
   never removed from `pg/pg_wal`. Planned: a WAL deletion thread removes the segments before
   `RaftState::first_segment`, the segment of the oldest entry compaction left
   ([backup.md](backup.md#5-wal-retention-and-raft-compaction)).
5. `set_wal_keep_from(LogSeqNumber)` for compaction (replacing `keep_old_logs`), and
   InstallSnapshot from the **oldest** entries (2 segments) instead of the latest
   `snapshot_entries` (decision 7 in [node.md](node.md#10-open-decisions)).
6. **Fixed (found by `node_test`):** on a short log the leader's walk-back could set
   `next_idx = 0`, so the next AppendEntries had `prev_log_idx = 0 - 1` and became an
   InstallSnapshot; and `send_install_snapshot` counted the `(0, 0)` sentinel as an entry, so
   `log_idx` underflowed and the follower installed an empty log, then aborted on `MDB_NOTFOUND`.
   The walk-back now stops at index 1 (the sentinel matches in every log), and the snapshot drops
   the sentinel (and falls back to AppendEntries from 1 if nothing else is left).
